# Orbit — Architecture

**Status:** Baseline architecture  
**Applies to:** initial Linux implementation  
**Read with:** `PRD.md`, `SECURITY.md`, `DECISIONS.md`

---

## 1. Architecture goals

Orbit's architecture should optimize for:

1. a narrow privilege boundary
2. native Git compatibility
3. low overhead
4. testable parsing and Git behavior
5. incremental product development
6. tolerance of repository changes made outside Orbit
7. typed communication between the frontend and Rust

The initial architecture deliberately avoids a cloud backend.

---

                       │ purpose-specific commands

The frontend is never a general shell client.

## 3. Technology baseline

Initial direction:

- Tauri 2.x
- React
- TypeScript
- Rust
- pnpm
- native system `git`

The initial scaffold should use the current compatible versions generated by the official Tauri project tooling rather than manually guessing dependency versions.

Dependencies are added only when a milestone provides a concrete need.

## 4. Frontend responsibilities

The React layer is responsible for:

- rendering application state
- user interaction
- navigation
- visual graph/diff presentation
- temporary UI state
- command invocation through typed wrappers
- accessible loading/error/empty states

The React layer is not responsible for:

- shell command construction
- direct Git process execution
- arbitrary filesystem traversal
- credential storage
- deciding whether destructive Git operations are safe
- parsing raw Git output when the parser belongs to repository logic

---

## 5. Rust responsibilities

Rust owns privileged and repository-specific behavior:

- native repository selection flow
- repository validation
- canonical repository identity
- Git process execution
- Git output parsing
- operation input validation
- repository-scoped authorization
- destructive-operation policy checks
- conversion of low-level failures into structured errors
- local application persistence that requires privileged filesystem access

Rust should return typed domain objects rather than exposing raw process stdout as the normal API.

---

## 6. Repository identity

A repository opened by the user becomes an authorized repository context.

The implementation should avoid making every frontend command accept arbitrary filesystem paths forever.

Preferred evolution:

```text
select_repository()
        ↓
RepositoryDescriptor {
  id,
  root,
  display_name,
  ...
}
        ↓
frontend uses repository_id
        ↓
repository-scoped commands
```

A process-local opaque `repository_id` can map to canonical paths in Rust.

Persisted recent-repository metadata may store canonical paths for reopening, but reopening must revalidate the repository.

This approach reduces accidental path confusion and narrows the command API.

---

## 7. Repository selection

Repository selection should be performed through a native dialog owned by the privileged side.

Preferred conceptual command:

```text
select_repository() -> RepositorySnapshot
```

The Rust side should:

1. open the native directory picker
2. handle cancellation
3. canonicalize/validate the selection
4. resolve the Git work-tree root
5. register an authorized repository context
6. return a typed snapshot

The WebView should not receive a generic "open arbitrary filesystem path and then do anything with it" capability.

---

## 8. Git execution boundary

All Git processes go through one internal boundary.

Conceptually:

```text
git/
├── process.rs
├── repository.rs
├── status.rs
├── history.rs
├── diff.rs
├── branches.rs
├── remote.rs
└── models.rs
```

`process.rs` should be the only low-level module that directly launches Git.

Other modules request domain operations.

Example:

```text
status::read(repository)
history::list(repository, page)
branches::switch(repository, branch)
```

rather than constructing process commands throughout the codebase.

---

## 9. Process execution model

Use direct executable invocation with separate arguments.

Never route Git through a shell for ordinary operations.

Conceptually safe:

```rust
Command::new("git")
    .current_dir(repository_root)
    .arg("status")
    .arg("--porcelain=v2");
```

Not allowed:

```rust
Command::new("sh")
    .arg("-c")
    .arg(format!("git status {}", user_input));
```

A direct process call prevents shell interpolation, but Git option/path ambiguity must still be handled.

Use `--` before user-controlled pathspecs when supported and required.

---

## 10. Machine-readable Git output

Prefer stable machine-readable formats instead of parsing human-oriented output.

Examples:

### Repository status

Prefer a porcelain status format suitable for programs, including branch metadata and NUL separation where useful.

Conceptual command:

```text
git status --porcelain=v2 --branch -z
```

The parser must:

- support known record types
- safely handle unusual filenames
- ignore explicitly extensible unknown headers when the Git format requires it
- include parser fixtures/tests

### Repository root

Use Git's own repository/work-tree resolution rather than manually walking for `.git` and assuming directory layout.

### Ref validation

Use Git's own ref-format validation where appropriate instead of inventing a partial branch-name grammar.

---

## 11. Typed IPC

Frontend commands should be narrow and product-oriented.

Good direction:

```text
select_repository()
get_repository_snapshot(repository_id)
get_commit_history_page(repository_id, cursor, page_size)
get_repository_changes(repository_id)
get_file_diff(repository_id, change_set_id, file_id, side)
stage_file(repository_id, file_id)
switch_branch(repository_id, branch_name)
```

Avoid exposing:

```text
run_shell(command)
run_git(args)
read_any_file(path)
```

Raw command composition is an internal Rust implementation detail.

TypeScript request/response types and Rust DTOs should stay synchronized.

If manual duplication becomes error-prone, introduce a deliberate schema/code-generation approach later rather than adding complexity during M0.

## 12. Domain model

Initial repository snapshot:

```ts
type RepositorySnapshot = {
  repositoryId: string;
  root: string;
  displayName: string;

  head: {
    oid: string | null;
    branch: string | null;
    detached: boolean;
    upstream: string | null;
    ahead: number | null;
    behind: number | null;
  };

  workingTree: {
    staged: number;
    unstaged: number;
    untracked: number;
    conflicted: number;
    clean: boolean;
  };

  recentCommits: CommitSummary[];
};

type CommitSummary = {
  oid: string;
  shortOid: string;
  parents: string[];
  subject: string;
  authorName: string;
  authorEmail: string | null;
  timestamp: number;
};
```

This is a conceptual contract, not a requirement to preserve exact property names forever.

Domain types should describe Git state without leaking process-specific parsing details.

## 13. Error model

Rust should return structured errors.

Conceptual shape:

```ts
type OrbitError = {
  code: string;
  title: string;
  message: string;
  operation?: string;
  recoverable: boolean;
  details?: string;
};
```

Candidate stable categories:

- `git_not_found`
- `not_a_repository`
- `repository_unavailable`
- `invalid_ref`
- `working_tree_conflict`
- `operation_in_progress`
- `authentication_failed`
- `network_failed`
- `permission_denied`
- `unsupported_repository_state`
- `git_command_failed`
- `internal_error`

Do not make UI behavior depend on matching human Git error strings when a stable application category can be determined.

Detailed diagnostics may preserve sanitized Git stderr for debugging, but user-facing messages should be contextual.

---

## 14. Cancellation and stale work

Repository reads may become stale when:

- a user opens another repository
- a branch changes
- an external Git process modifies state
- a newer refresh starts

Long-running reads should be designed so stale results do not overwrite newer state.

Network operations should support cancellation if the underlying implementation can do so safely.

M0 does not need a universal cancellation framework, but APIs should avoid assuming every call is instantaneous.

---

## 15. Refresh architecture

Orbit must tolerate external mutations.

Potential sources:

- terminal
- IDE
- file editor
- Git hooks
- other local processes

Initial implementation can combine:

- explicit refresh after Orbit operations
- refresh on window focus
- a conservative watcher strategy when added

Do not introduce aggressive fixed-interval polling.

The final watcher strategy should be researched during the milestone that needs it.

---

## 16. Frontend state strategy

Do not add a global state-management library by default.

Start with:

- React state
- context only where justified
- feature-local hooks
- typed Tauri client wrappers

Introduce a state/query library only after a concrete complexity appears, such as:

- cached asynchronous repository queries
- request deduplication
- invalidation across many views
- complex optimistic updates

The dependency should solve an observed problem, not anticipate one.

## 17. Graph architecture

The commit graph should be treated as a model + rendering problem.

Separate:

1. Git history data
2. graph lane/topology calculation
3. virtualized list/window
4. visual renderer
5. selection and interaction

Do not couple Git parsing directly to SVG/canvas/DOM rendering.

M1 locks the following split:

```text
native Git log + for-each-ref
        ↓ bounded NUL-framed parsers
Rust CommitHistoryPage + opaque ordered-plan cursor
        ↓ purpose-specific typed IPC
pure frontend lane reducer + carried continuation state
        ↓
accessible DOM rows + presentation-only per-row SVG
```

History uses topological order and starts from a Rust-owned snapshot of commit-bearing local
branches, remote-tracking branches, tags, and HEAD. Ref metadata comes from a separate bounded
`for-each-ref` query so annotated tags, symbolic refs, and ref kinds remain typed rather than being
parsed from decoration text.

At session start, one bounded `git log --topo-order` walk records at most 1,001 full OIDs: the 1,000
commits the session may emit plus one truncation sentinel. Page reads request metadata only for the
next Rust-owned OID slice with `git log --no-walk=unsorted`. This preserves the exact order of one
continuous topological walk without an ever-growing `--skip` value or reconstructing Git's lost
traversal queue from frontier tips. The frontend never supplies revision expressions. The policy
defaults to 100 commits per page, accepts 1 through 200 per request, caps starting tips at 512, and
stops at 1,000 loaded commits with an explicit limit flag. Invalid request sizes and bound failures
are structured errors, never silent truncation.

Sessions are process-local, bound to the opaque repository ID and its revalidated canonical root,
limited to eight active entries, and expired after 15 minutes idle. A continuation atomically marks
its cursor in flight, rejects concurrent reuse, and rotates it only after the next page succeeds.
Capability or Git page-read failures restore the old cursor for retry. The oldest available session
is evicted when the active-session bound is reached; in-flight sessions are not evicted. A process
restart, unknown/reused cursor, repository mismatch, repository disappearance, or changed root
identity requires a new session. External HEAD/ref movement does not change an existing session:
its starting HEAD, refs, and ordered OID plan remain the snapshot, and typed refs are returned only
on its first page. Explicit refresh starts a new snapshot.

The frontend derives graph lanes from semantic parent relationships. Lane identity is stable and
monotonic across appended pages; visual columns may compact when lanes close. First-parent
continuation is preferred, secondary parents open lanes to its right, and converging lanes are
deduplicated.

B2a implements this as a pure `reduceTopology` TypeScript reducer. It returns semantic rows, lane
transitions, parent edges, ref annotations, and explicit continuation stubs without pixel
coordinates, SVG paths, DOM objects, or React lifecycle dependencies. Its continuation state keeps
active lane IDs and expected parent OIDs stable across B1 pages; processed OIDs are bounded by the
B1 session ceiling.

B2b now consumes those rows in an accessible fixed-height commit list. Commit metadata, focus,
selection, refs, and details remain ordinary DOM content. Each row owns a narrow `aria-hidden` SVG
strip for topology only. The strip maps stable lane IDs to compact visual columns and uses fixed
geometry; it never recomputes Git relationships. Active continuation stubs pin unresolved visual
lanes through the last loaded row until a later page reconnects them. No graph, animation,
global-state, or virtualization dependency is approved initially. Profile 100, 500, and 1,000
loaded rows on a recorded Linux environment before deciding whether fixed-row windowing is
necessary.

The exact command framing, cursor state, type model, lane invariants, renderer comparison, and
security mitigations are recorded in `M1_COMMIT_GRAPH_RESEARCH.md`.

## 18. Diff architecture

M2 keeps change discovery, diff acquisition, patch parsing, and rendering as separate layers.
Detailed state comes from one hardened, NUL-delimited porcelain v2 status read. Rust parses byte
paths, derives the M0 summary from the same semantic entries, and returns independent staged and
unstaged facets. Conflicts and submodules are explicit states rather than ordinary text diffs.

React receives only an opaque change-set ID and opaque file IDs. The process-local Rust registry
retains byte-exact current/origin paths and the parsed change facets. Purpose-specific diff IPC
accepts the authorized repository ID, change-set ID, file ID, and a closed staged/unstaged side; it
never accepts paths, revisions, pathspecs, format strings, or Git arguments.

The first M2 slice implements `get_repository_changes` with this detailed parser and registry.
Change sets are repository/root-bound, limited to eight active entries, expire after 15 minutes
idle, and are replaced only after a new status read succeeds. A monotonic Rust-owned generation is
reserved before blocking repository/status work; only the latest generation for that repository
may install. This prevents an older worker from invalidating a newer successful refresh when
completion order differs from request order. Failed or superseded refreshes leave the prior valid
change set intact when repository authorization remains valid.

The second M2 slice implements `get_file_diff` with the authorized repository/change-set/file tuple
and a closed staged/unstaged side. It revalidates the root and fresh semantic status before one
bounded acquisition, then returns typed text hunks or an explicit binary, conflict, submodule,
too-large, or unavailable state. No raw patch or path authority crosses IPC.

Staged patches use `git diff --cached`; unstaged patches use `git diff`. Untracked regular files and
symlinks use a bounded Linux `git diff --no-index` comparison against `/dev/null`. All path
arguments are Rust-owned and follow `--`. One numstat-plus-patch response provides machine-framed
binary classification and unified patch data from the same Git invocation. Rust validates the
numstat identity before a pure Rust patch parser produces typed hunks and lines. Patch header paths
are never authoritative.

Rename/copy reads supply both Rust-held paths. A facet-specific `--diff-filter=R` or
`--diff-filter=C` is applied after Git's bounded detection so a modified copy source cannot add a
second numstat/patch record to the selected-file response.

Binary, conflicted, submodule, too-large, unsupported-encoding, special-file, timeout, stale, and
unavailable results are explicit. Text patches must be valid UTF-8 initially; Orbit does not
lossily decode them. Status and diff output, entries, retained paths, hunks, lines, registry state,
diagnostics, and process duration all have fixed limits. A non-following file-type check and a
GitRunner deadline protect untracked reads from special-file and replacement races.

A successfully refreshed status list replaces the prior change set. Diff reads reauthorize the
repository, validate all opaque handles, and compare a fresh hardened status record before
acquisition. This is read-committed consistency: the selected Git command sees current content,
while change-set IDs and frontend request generations prevent its response from being attached to
a newer list.

The exact command policy, byte/path model, initial bounds, experiments, and deferred cases are
recorded in `M2_CHANGES_DIFF_RESEARCH.md`. No syntax-highlighting, file-watching, graph, database,
or state-management dependency is approved by this architecture.

## 19. Persistence

Core repository state lives in Git, not in Orbit.

Orbit persistence is limited to application metadata such as:

- recent repositories
- UI preferences
- theme
- layout preferences
- optional provider connection metadata that is safe to persist

Do not create a database in M0 unless a concrete need appears.

A small app-data file or similarly simple mechanism is preferable for early local metadata.

Never persist credentials in plaintext.

---

## 20. Authentication boundaries

Basic Git remote operations should delegate authentication to Git and the user's existing environment.

Orbit should not:

- collect SSH private keys
- implement an SSH key vault in the MVP
- duplicate Git credential helpers
- persist arbitrary passwords

Provider API authentication, when introduced, is a separate feature and must use platform-appropriate secure credential storage.

## 22. Testing strategy

### Rust unit tests

Test:

- status parsing
- history parsing
- validation helpers
- structured error mapping
- safety rules

### Rust integration tests

Create temporary Git repositories for behavior such as:

- empty repository
- initial branch with no commits
- normal commit history
- modified file
- staged file
- untracked file
- rename
- detached HEAD
- merge commit
- conflict state

Tests should use the actual `git` executable where integration behavior is being validated.

### Frontend tests

Test:

- state rendering
- error/empty/loading states
- user interactions
- transformations around typed command results

Do not mock every layer when an inexpensive lower-level test can validate the real behavior.

## 23. Validation gates

A milestone should not be considered complete unless the relevant checks pass.

Initial expected gates:

- frontend formatting/lint rules once configured
- TypeScript typecheck
- frontend tests once introduced
- `cargo fmt --check`
- `cargo clippy` with an agreed warning policy
- Rust tests
- Tauri build/check appropriate to the environment

Do not claim packaging, memory, startup-time, or performance results unless measured.

## 24. Observability and diagnostics

Orbit should eventually provide enough diagnostics to debug failures without requiring raw stack traces in the main UI.

Potential diagnostic fields:

- Orbit version
- OS
- Git version
- operation
- structured error code
- sanitized command metadata
- sanitized stderr

Never include:

- credential values
- authorization tokens
- private keys
- full environment dumps by default

---

## 25. Dependency policy

Before adding a dependency, answer:

1. Which milestone requirement needs it?
2. Can the platform/runtime already provide the behavior?
3. What is its maintenance and security cost?
4. Does it materially affect binary size or performance?
5. Is it cross-platform if the architecture assumes that?
6. Can it be isolated behind a replaceable boundary?

Avoid adding packages solely because they are common in other React or Tauri projects.

---

## 26. Architecture evolution rule

The architecture is intentionally small at the beginning.

When the implementation reveals a real limitation:

1. document the problem
2. research alternatives
3. update `DECISIONS.md`
4. implement the smallest justified change
5. add tests for the behavior that required the change

Do not perform speculative rewrites between milestones.
